# Implementation Plan: Doit Goal Tracker — Initial Page Setup

**Branch**: `001-doit-goal-tracker` | **Date**: 2026-10-10 | **Spec**: [spec.md](./spec.md)

## Summary

Build the initial "doit" goal-tracking page: a two-column board (active goals left,
sorted soonest-deadline-first with a days-left indicator and a due-soon highlight;
completed goals right, sorted most-recently-completed-first), an "Add Goal" button that
opens a shadcn `Dialog` form (title + end date), a per-goal checkbox that completes and
moves a goal, and a per-goal delete control with a confirmation step. All goals persist
in the browser via `localStorage` (no backend). Styling uses Tailwind CSS v4's `@theme`
directive to declare a light, pastel design-token palette consumed by shadcn/ui
components; `date-fns` computes and formats the days-remaining values. No automated
tests are created, per the project constitution.

## Technical Context

**Language/Version**: TypeScript ^5 on Next.js 16.4.0 (App Router) / React 19.3.0

**Primary Dependencies**: Tailwind CSS ^4 (`@theme` design tokens), shadcn/ui component
primitives (Radix UI-backed `Dialog`, `Checkbox`, `Button`, `Input`, `Label`, `AlertDialog`,
installed as owned source under `components/ui/`), `date-fns` for date math/formatting

**Storage**: Browser `localStorage` only (single JSON array under one key) — no backend,
no database, no user accounts (per spec Clarifications)

**Testing**: None — unit, integration, and e2e tests are explicitly out of scope and MUST
NOT be added (Constitution Principle V, NON-NEGOTIABLE). Verification is TypeScript
compilation, `eslint`, and manual browser review at mobile and desktop widths.

**Target Platform**: Web browser (client-rendered), responsive from 375px to 1440px+

**Project Type**: Single Next.js web app (no separate frontend/backend split; no API
routes needed since all state lives in the browser)

**Performance Goals**: All interactions (add/complete/delete) MUST reflect in the UI
within one render frame — no network round-trip exists since there is no backend

**Constraints**: No server-side persistence; new dependencies beyond the existing stack
(shadcn/ui, date-fns) MUST be justified against Constitution Principle IV (see
Complexity Tracking below); no automated test tooling may be introduced

**Scale/Scope**: Single user, single device/browser profile; realistically tens to a few
hundred goals — no pagination or virtualization required for this scope

split and no API routes, since all data lives client-side in `localStorage`. `app/`
keeps routing/shell files only; all board logic lives in `components/` (reusable,
independently reviewable pieces) and `lib/` (framework-free helpers), following the
existing repository convention of a flat `app/` directory.

## Complexity Tracking

> Principle IV (Minimal Dependencies) requires justification for dependencies beyond
> the existing stack. Both additions below were explicitly requested by the project
> owner for this feature and are justified rather than incidental.

| Addition | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| shadcn/ui primitives (Radix-backed `Dialog`, `Checkbox`, `AlertDialog`, `Button`, `Input`, `Label`) | The modal form, completion checkbox, and delete-confirmation step all need correct focus-trapping, keyboard, and ARIA behavior. | Hand-building accessible dialog/checkbox/alert-dialog behavior from scratch is error-prone and would duplicate well-tested, widely-used primitives for no UX benefit; shadcn components are copied into the repo as owned source (not a hidden black-box dependency), keeping Principle I (Clean Code) reviewability intact. |
| `date-fns` (specifically `differenceInCalendarDays`, `format`) | Days-left math (FR-002, FR-003) must be correct across month/year boundaries and must not drift due to time-of-day/DST. | Hand-rolled date-diff logic using raw `Date` math is a common source of off-by-one bugs at boundaries; `date-fns` is tree-shakeable (only the two functions used are bundled), so the cost is a few KB, not a full date framework. |
